# 납품 라인(deliveries) 수집 예산 — 제약과 문제

> 아이디어를 내기 위한 문제 정리. 해법은 일부러 적지 않았다.
> 수치 기준: 2026-10-14 15:02 KST, 데이터셋 `20261010-r5` → silver(`3178ec7`).
> 15:30 정정: 대회 문서(rules.md·api.md)를 다시 읽고 5절을 고쳤다. 제출 한도(하루 50·누적 100)와 대회 `items/{item_id}`가 라인을 준다는 점 때문에 문제의 모양이 바뀌었다.

## 문제

등재별 납품요구 라인(`GET /v1/listings/{id}/deliveries`)은 데이터 API로만 받을 수 있고, 데이터 API는 시간당 3,600회로 묶여 있다.
라인을 **어느 물품에 대해, 언제, 얼마나** 받을지 정해야 한다. 같은 예산을 등재 상세·물품 상세·검색·MCP도 나눠 쓴다.

## 1. 라인이 있어야 내릴 수 있는 판단은 무엇인가

데이터셋에는 키(계약, 물품)별 **합계**(`dlv_*`)가 이미 있다. 라인은 그 합계를 쪼갠 것이다.

| 판단 | 데이터셋 합계로 | 라인이 더하는 것 |
|---|---|---|
| 후보 순위(잠재 금액 상한) | 가능 — `items.dlv_amount` | — |
| 수량·평균 단가 | 단위가 하나인 키만 가능. 단위가 섞였거나 비어 수량이 null인 키 **1,306개** | 라인별 단위·수량 |
| 실제 구매 단가(등재가와 다른 구매, 할인, 차수 변경) | 불가 — 합계만 있다 | 라인별 `unitPrice`·`contractUnitPrice`·차수 |
| 대회 fact 미리 보기 | 불가 | `request_no`·`line_no`가 fact와 같은 축. 단, 대회 `items/{item_id}`가 fact를 직접 준다(아래 4절) |
| 최근성·주문 분포 | 첫·마지막 주문일만 | 라인별 날짜·기관 |
| 전량 취소 | 전량 취소 키 수(5,811)만 | 라인별 0 라인 |

**채점 값은 라인이 아니라 대회 fact다**(C = `comparable_amount_krw`, Q = `quantity`). 데이터셋과 deliveries는 둘 다 추정치다.

## 2. 데이터 API 예산

| 항목 | 값 | 출처 |
|---|---|---|
| 한도 | 3,600회/시간, `rateLimit.kind = "window"`, `windowMs = 3600000` | `/v1/me` 응답(10/14) |
| 검색 | 별도 120회/분. 우리 Go 클라이언트는 검색 때 시간 버킷도 함께 기다린다(서버가 시간 버킷에서도 빼는지는 미확인) | docs/API.md, `internal/api/data` |
| 공유 | REST와 MCP가 같은 예산. 이 Claude Code 세션의 MCP 탐색도 여기서 빠진다 | 대회 문서 |
| 무료 | `/v1/me`는 차감되지 않음 | 대회 문서 |
| 남은 시간 | 마감(10/25 23:59 KST)까지 **273시간** → 이론상 최대 **982,630회** | 계산 |
| 이월 | window 방식이라 쓰지 않은 시간의 한도는 쌓이지 않는다. 고정 window인지 슬라이딩인지는 미확인 | `/v1/me` |
| 토큰 만료 | 2026-10-27(마감 뒤) | `/v1/me` |

같은 버킷을 쓰는 다른 수요: `listings/{id}`(스펙·첨부), `items/{id}`(연결 등재 최대 100), `listings/resolve`, 검색, MCP.
**후보 1건을 검증하는 데 데이터 API를 몇 번 부르는지는 아직 재지 않았다.**

## 3. deliveries 엔드포인트의 성질

- **등재 단위로만** 부를 수 있다. 물품 단위 엔드포인트는 없다.
- `limit ≤ 1000`, offset 페이지. `final=1`이면 최종 차수 라인만(전량 취소 0 라인 포함).
- 같은 (계약, 물품)을 공유하는 등재는 같은 라인을 돌려준다 → **납품 키당 등재 하나**면 된다.
- 응답에 `finalSummary`(최종 차수 합계)가 항상 들어 있다 — 첫 페이지만 받아도 합계는 안다.
- 404 = 이 카탈로그에서 제공하지 않음(가격 정상이라는 뜻이 아님).
- 데이터 API 릴리스(`r20261011T012137`)와 데이터셋 릴리스(`20261010-r5`)가 다르다. 데이터셋 납품 기간은 2025-10-10 ~ 2026-09-27이고, API 라인이 그 뒤 주문까지 담는지는 미확인.
- 확인된 차이: `finalSummary.lineCount`는 0 라인을 세고 데이터셋 `dlv_lines`는 세지 않는다(같은 등재에서 5 vs 4). 금액 합은 같다.

## 5. 대회 쪽 사실 (데이터 API 예산을 쓰지 않는 것들)

| 항목 | 내용 | 미확인인 점 |
|---|---|---|
| 채점 대상 범위 | 조달 상품 **전체**(물품 약 99만 개, rules.md 1절). 서버는 조회·등록된 물품만 그때 스냅샷으로 가져온다 | `products_total` 46,857은 스냅샷이 만들어진 물품 수로 추정(채점 대상 범위가 아님) |
| 제출 한도 | 하루 50건·누적 100건(`/me` limits, 하루 경계 KST 자정). 거절은 안 셈, 철회는 안 돌아옴 | — |
| `items/lookup` | 100개/호출, 스냅샷 안 만듦, 제출 횟수 미사용, `state ∈ available·claimed·claimed_by_me·reform_found·not_found`(not_found = 상품 데이터에 없는 번호), 등재번호도 받음. 대회 API는 속도 제한 없음 | — (우리는 초당 1회 이하로 운영) |
| `items/{item_id}` | 첫 호출 때 물품 요약·등재 목록·**최종 차수 납품 라인**을 가져와 스냅샷으로 고정(이후 모두에게 같은 값). fact마다 `fact_id`·`request_no`·`line_no`·`unit`·`tax_basis`·`basis_id`·`unit_price_krw`·`quantity`·`comparable_amount_krw`·`scorable`. 2,000줄 넘으면 금액순으로 자름. **새 물품 조회만 참가자당 분당 30건**·서버 전체 상한(429 `RATE_LIMITED`, 횟수 안 셈). 데이터 API 예산을 쓰지 않는다 | `snapshot.fetched_at`으로 누가 먼저 조회했는지 알 수 있는지 |
| 선착순 | 같은 item_id는 먼저 등록한 1명만. 선점 4,304건(10/14 11:55) | 어떤 물품이 선점됐는지는 lookup·found로만 안다 |
| 경쟁 상황 | 고액 물품은 초반에 대부분 선점된 것으로 추정(RULES.md) | 추정 |
| 풀리는 물품 | 철회·반려되면 물품이 다시 풀린다(`watch`로 감지 예정) | 빈도 |

## 6. 열린 질문

1. 라인 데이터가 실제로 **바꾸는 결정**은 무엇인가? 그중 대회 fact가 대신할 수 있는 것은?
2. 예산을 어떻게 나눌까: 넓게 훑기 · 상위 후보 깊게 검증 · 철회 감지 직후를 위한 예비분.
3. 무엇부터 받을까: 납품 금액? 선점 가능성? 시중가 근거를 찾을 가능성? 단가 이상치 정도?
4. 쓰지 않은 시간의 한도는 사라진다. 사람이 검토하느라 쉬는 시간의 예산을 어떻게 쓸까?
5. 한 번 받은 라인은 언제 다시 받아야 할까(원장 갱신, 대회 스냅샷과의 차이)?
6. 라인이 필요한 판단을 대회 fact(데이터 API 0회)로 얼마나 대신할 수 있을까? 제출이 100건뿐인데 라인은 몇 물품분이 필요할까?
7. 대회 fact 스냅샷 고정은 언제 일어나게 하는 것이 좋은가?

## 7. 아직 모르는 사실 (싸게 확인할 수 있는 것)

- 납품 물품 중 이미 선점된 비율(무작위 표본 vs 금액 상위) — lookup 10회씩.
- 같은 물품에 대해 deliveries 라인과 대회 fact가 얼마나 일치하는지 — 1~2건 비교.
- 후보 1건 검증에 드는 데이터 API 호출 수.
- 데이터 API window가 고정형인지 슬라이딩인지 — `/v1/me`(무료)를 지켜보면 알 수 있다.
- API 라인이 2026-09-27 이후 주문도 담는지.
