## 지금 이어서 할 일 (2026-11-05 기준)

사용자가 먼저 생각을 말하고, Claude는 그 뒤에 의견을 붙인다(CLAUDE.md 「작업 방식」). **11/05부터는 포트폴리오 마감 때문에 속도가 우선이다.** 큰 방향은 정했으므로 세부는 Claude가 권장안을 채택해 구현하고 결정 이력에 "권장안 채택"으로 남긴다. 비용이 드는 실제 LLM 실행, 커밋·푸시, 외부로 나가는 일은 계속 묻는다.

### 11/03~11/04에 정한 것 (이유와 버린 안은 아래 결정 이력)

- **다음 작업 순서**: A(평가)와 B(에이전트)를 한 묶음으로 하고, 순서는 답안지 양식 → 채점기 → 에이전트. D(웹 화면)는 그 뒤, C(1부 게이트의 hard-05 파렛트 환산 문제)는 뒤로 미룬다.
- **채점**: ① 근거 검증(답안을 보관 원문·조달 물품 정보와 대조, 정답 불필요)과 ② 정답 대조(`cases.jsonl`, 합성 데이터에만 있음)를 둘 다 둔다. 채점기는 에이전트와 같은 판단 로직을 쓰지 않는다.
- **2부의 상정**: 대회 제출이 아니라 실제 사용자의 검증 도구로 쓸 수 있는가. 선점된 건도 대상이다.
- **답안지 양식**: 8개 항목을 모두 정했다. 명세는 [`studio/docs/answer-sheet.md`](../studio/docs/answer-sheet.md)에 있다. 요지: 라벨 5종(판단 보류 포함)만 LLM이 내고 가격 차이는 코드가 계산한다. 속성 대조표의 줄마다 코드가 확인해 접거나 펼친다. 근거는 줄 번호 + 글자로 도구가 확인해 ID를 준다. 위험(`danger`)·판단 보류·펼친 줄·"시중가 대비 N배" 결론은 사람에게 가고, 나머지는 자동 통과한다.
- **결정 2(ADR)**: 결정마다 ADR을 두지 않는다. 설계의 현재 모습은 명세 문서에, 어떻게 정했는지는 이 문서의 결정 이력에 적는다.
- **평가 지표**: 7개 항목을 정했다. 명세는 [`studio/docs/scoring.md`](../studio/docs/scoring.md)에 있다. 요지: 중심 점수는 결론(N배 / 지적할 것 없음)의 정밀도·재현율이고 라벨 표는 진단이다. 판단 보류는 분모에서 빼고 보류율·보류의 질을 함께 본다. 비교 단가는 원 단위 정확 일치가 정답이고 오차는 방향과 원인까지 나눈다. 이유 점수를 따로 매기고 동급부터 시작한다. 처리 지표는 사건 단위로 시작한다. 점수 하나로 합치지 않고 점수표에 "반드시 0건" 조건 3개를 둔다. 완화 기준은 형식만 정했다(실데이터만, 버전이 바뀌면 누적 리셋). 답안지 명세 7절에 필수 속성 누락·단정 표현 → 사람을 더했다.

- **구현 구성(11/04)**: 백엔드는 Python, 웹 화면은 TypeScript. 기존 Go는 다시 짜지 않고 작은 함수 단위로 쓴다. 에이전트의 도구는 Python MCP 서버 하나(stdio)가 제공하고 일부 도구가 안에서 Go를 부른다. 판단 로직은 `studio/sheet` 라이브러리에 둔다. 채점기는 읽기만 한다. 스키마 원본은 JSON Schema 파일이다. 저장은 JSON 파일(실행마다 디렉터리, 사건마다 답안지)이다. 명세는 [`answer-sheet.md`](../studio/docs/answer-sheet.md) 13절에 있다.

- **1차 구현(11/05)**: 워크플로우 전체가 돈다. 합성 데이터 → 사건마다 MCP 도구 서버(stdio) + 에이전트 도구 루프 → 답안지 → 확인·처리 결정 → 웹 검토 화면에서 사람 판정 → 채점기(정답 대조 + 사람 판정 일치 + 완화 기준 기록). LLM 없는 규칙 기준선으로 51건이 6초에 돈다(`make studio-baseline`). 실제 LLM(OpenAI) 실행은 아직 하지 않았다(API 키 없음). 명령은 [`studio/README.md`](../studio/README.md) 「워크플로우」.

### 그 뒤에 정할 것 (아직 다루지 않음, 순서도 미정)

- 에이전트 범위: 판매처 페이지를 **찾는 일**까지 할지, 주어진 후보 페이지를 **판정**만 할지. 찾기까지 하면 가짜 판매처에 검색이 필요하다.
- 도구와 권한의 세부: 지금 도구는 원문 줄 조회, 조달 물품 정보 조회(P 없음), 사이트 정책 조회(정책 페이지가 없어 늘 "없음"), 근거 첨부, 계산기 + 실행기의 submit_answer·review_title(명세 5절). 정책 페이지를 읽을 때 같은 사이트 안으로만 제한할지 등. 가짜 판매처에 정책 페이지가 있어야 하고, 그 페이지도 주입 경로가 될 수 있다.
- 모델과 비용: 지금 기본값은 OpenAI `gpt-6.1-terra`, reasoning effort medium, 반복 3회. 이야기한 기본안(작은 모델 1차, 애매한 건 큰 모델)은 반복 실행을 다른 모델로 돌리는 기능이 필요하다(아직 없음, OpenAI라면 Terra 1차 → Sol). 한 번 실행할 때의 비용 상한, 평가 반복 횟수(채점 명세 5절).
- 품목별 동급 허용 차이 기준: 이유 점수는 "어디까지가 동급인가"를 정하지 않는다(채점 명세 3.6절). 필수 속성 목록과 함께 정할 수 있다. 합성 정답의 기준을 그대로 베끼면 점수가 부푼다.
- 가상 렌더링 머신(11/03 사용자 요청, **미래의 개선 사항**으로 미룸): 헤드리스 브라우저로 JS 페이지를 그려 LLM에게 준다. 따질 점: 지금 정답 파일은 "JS 페이지는 못 읽는다"를 전제로 빈 페이지 5건을 근거 부족으로 둔다(가짜 판매처는 `/static/app.js`를 내주지 않는다). 렌더러를 넣으면 가짜 판매처가 실제로 그려지는 스크립트를 내주고 생성기의 정답도 바뀌어야 한다. 그린 결과(DOM)를 원문으로 보관·해시한다. 남의 자바스크립트를 실행하므로 데모에서는 외부 요청을 막는다(CLAUDE.md 규칙 3). 봇 차단을 우회하는 수단으로 쓰지 않는다. 지금까지 studio는 표준 라이브러리만 썼는데 큰 의존성이 생긴다.
- 합성 데이터 보강: 가격은 있는데 부가세 표기가 없는 사례(지금 표기 없는 8건은 모두 가격 자체가 없다), 가짜 판매처의 사이트 정책 페이지(명세 12절). 주입 사례를 늘릴지(`danger` 0건 조건을 hard-13 1건으로만 시험한다), 규격이 실제로 다른 동급 사례를 늘릴지(지금 hard-01 1건).
- 워크플로우의 끝: 1부의 가짜 제출을 계속 끝 단계로 둘지, 검증 결과(보고서)가 끝인지. 11/03 "실제 사용자의 검증 도구"로 상정을 바꾸면서 생긴 질문이다. 실제 사용자를 누구로 상정할지도 함께.
- 사람의 결정이 실제로 작동하게 하는 화면 정책: "다른 물건" 판정에도 가격 차이를 보여 줄지(배율이 사람을 끌어당길 수 있지만, 잘못된 "다른 물건"을 잡을 단서도 된다). AI 답을 먼저 보여 주면 그대로 승인하기 쉬운 문제(자동화 편향)를 어떻게 줄일지.
- (웹 설계 단계) 보류 건의 사람 판정을 에이전트 개선(프롬프트·필수 속성 목록·동급 기준)에 쓰는 경로, 개선에 쓴 사례와 평가에 쓰는 사례를 나누는 방법(채점 명세 3.3절).
- 웹 화면의 사용자 구상(11/03): 대조표의 줄이 신뢰도에 따라 자동으로 접히거나 펼쳐지고, 줄을 열면 인용·출처 같은 근거가 보인다. 확신이 높아도 라벨을 결정한 줄은 펼쳐 둘지는 화면 단계에서 정한다.
- 1부 게이트 한계(hard-05) 처리: 게이트를 고칠지(단위 환산을 근거에 명시하면 통과), 사람에게 넘길지.
- 작업 대기열·상태 전이·재시도·비용 상한(워커), 사이트 정보 저장소의 유효기간과 저장 기술.
