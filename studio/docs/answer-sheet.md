# 답안지 명세 — 에이전트가 내는 판정 결과의 형식과 처리 규칙

> **상태: 설계 확정(2026-11-03, 13절 구현 구성은 11/04), 1차 구현(11/05).** 사용자와 함께 정한 내용을 한곳에 모은 문서다. 결정마다 누가 정했는지, 버린 안과 이유는 [`docs/WORKLOG.md`](../../docs/WORKLOG.md) 「결정 이력」에 있다. 이 문서는 "지금 정해진 모습"을, 결정 이력은 "어떻게 여기까지 왔나"를 적는다. 결정이 바뀌면 이 문서를 고치고 결정 이력에 한 줄을 더한다.

답안지는 에이전트가 사건(조달 물품 하나와 판매 페이지 하나의 짝)마다 내는 JSON이다. 채점기가 읽고, 나중에 웹 검토 화면이 띄운다. 1부 제출 본문(claim)과는 따로 두고, 결론이 "시중가 대비 N배"일 때만 변환기가 제출 본문으로 바꾼다.

## 1. 원칙

- **판단은 LLM, 숫자와 확인은 코드.** 페이지를 읽고 값을 고르고 같은 물건인지 판단하는 일은 LLM이 한다. 코드는 페이지 구조에 맞춰 값을 미리 뽑지 않는다. 비교 단가·배율·가격 차이 기준은 코드가 계산하고, LLM이 낸 근거와 값이 맞는지도 코드가 확인한다.
- **자동 통과는 페이지 글이 조작할 수 없는 신호에만 기댄다.** LLM의 자기 보고 확신도는 참고값이다. 숨은 지시문이 "확신 높음"이라고 쓰게 만들 수 있기 때문이다.
- **틀렸을 때 피해가 큰 쪽은 사람이 본다.** "지적할 것 없음"을 잘못 통과시키면 하나를 놓치지만, "시중가 대비 N배"를 잘못 내보내면 근거 없는 지적이 된다(CLAUDE.md 규칙 6).
- **사람의 판정이 쌓여 자동화의 근거가 된다.** 처음에는 사람이 보고, 평가 지표로 성숙도를 확인한 만큼 자동 통과를 넓힌다.

## 2. 흐름

```
조달 물품 정보 + 판매 페이지 원문(보관본)
   │
   ▼ 코드: 입력 준비
   │   HTML → 태그를 뺀 줄 목록(줄 번호 JSON)
   │   경고 탐지(AI에게 하는 말, 숨은 글) → AI에게 하는 말은 입력에서 뺀다
   ▼
에이전트 1회 실행 (도구로 근거 조회·첨부)
   │   라벨, 대조표, 읽은 값 + 계산식, 판정 이유, 제목 더블체크·보충
   ▼ 코드: 확인(객관 신호)
   │   근거 ID, 값 비교, 계산식 재계산, 부가세 두 가정, 필수 속성 누락, 단정 표현
   ├─ 모든 줄 통과 ──────────────▶ 그 1회 결과를 쓴다
   └─ 통과 못 한 줄이 있음 ──────▶ 에이전트를 여러 번 실행, 일치도를 기록. 그 줄은 펼친다
   ▼ 코드: 처리 결정 (7절)
   ├─ 자동 통과
   └─ 사람 검토 (웹 화면)
   ▼
(결론이 "시중가 대비 N배"이고 승인되면) 변환기 → 1부 제출 본문
```

## 3. 입력 준비 (코드)

- **줄 번호 원문.** 보관한 원문 HTML에서 태그를 빼고 줄로 나눠 `[{"line": 1, "text": "…", "hidden": false}, …]`로 만든다. 화면에 안 보이게 처리된 글(`display:none` 등)은 `hidden: true`로 표시한다. 줄 나누기는 페이지 내용을 이해하지 않는 전처리라 어떤 페이지에든 똑같이 적용한다. 규칙이 바뀌면 줄 번호도 바뀌므로 **나누기 규칙의 버전**을 원문 해시와 함께 기록한다.
- **경고 탐지.** 6절의 규칙으로 코드가 탐지한다. 탐지된 AI에게 하는 말은 **에이전트 입력에서 뺀다.** 사람 화면에는 경고와 함께 그대로 보여 준다.
- **읽은 방식.** 지금은 정적 HTML만 읽는다(`static`). 자바스크립트로 그려지는 페이지를 그리는 가상 렌더링 머신은 미래의 개선 사항이다(11절).

## 4. 답안지의 칸

| 칸 | 채우는 쪽 | 확인 |
|---|---|---|
| 읽은 방식(`static` / `rendered`) | 코드 | |
| 라벨: 같은 모델 · 동급 · 다른 물건 · 근거 부족 · **판단 보류** | LLM | 채점 ② 정답 대조 |
| 대조표 줄: 속성, 조달 값, 판매 값, 비교 결과, 확신도 | LLM. 품목별 **필수 속성** 목록은 코드가 가지고, LLM은 줄을 더할 수 있다 | 값 비교와 근거 확인 → 접힘/펼침 |
| 반복 일치도(예: 5회 중 4회 동급) | 코드(여러 번 실행한 경우) | |
| 읽은 값: 판매가, 부가세 표기, 판매 단위, 환산 정보 | LLM(각각 근거 ID) | 근거 확인 |
| LLM 계산: 계산식(예: `ceil(400 × 25 × 1.1)`)과 비교 단가 | LLM(계산기 도구로 계산) | 코드가 식을 다시 계산하고 코드 계산과 대조 |
| 코드 계산: 비교 단가, 배율, 가격 차이 기준 통과, 부가세 가정 | 코드 | 채점 ② 정답 대조 |
| 근거: ID, 출처(조달 물품 / 판매 페이지 / 사이트 정책), 줄 번호, 글자 | 근거 첨부 도구(코드) | 첨부할 때 확인 |
| 경고: `danger` · `주의` · 표시만 | 코드 | |
| 제목·결론 | 코드 틀 | LLM이 더블체크(동의 여부)하고 보충 |
| 판정 이유, 보충, 판단 보류 사유 | LLM. 값은 직접 쓰지 않고 근거 ID로만 가리킨다 | 단정 표현 검사 |
| 처리 결과(자동 통과 / 사람)와 이유 | 코드 | |
| 실행 기록 | 실행기 | |

- **라벨만 LLM이 낸다.** 결론(가격 차이 있음 / 지적할 것 없음)은 라벨과 코드의 가격 차이 계산으로 정해진다. 같은 모델이나 동급이고 가격 차이 기준(P ≥ 1.2×M 또는 P − M ≥ 100만 원)을 넘으면 "시중가 대비 N배"다. 대회의 선점 상태는 보지 않는다(실제 사용자의 검증 도구를 상정한다).
- **판단 보류**는 근거는 있는데 확신하지 못하는 경우다. 페이지에 근거가 없는 "근거 부족"과 다르다. 판단 보류에는 사유를 반드시 쓰고, 어느 줄 때문인지 가리킨다.
- **필수 속성 목록**은 "그 물건을 살 때 무엇을 보나"로 쓴다. 합성 데이터 생성기의 함정 목록을 베끼지 않는다(시험지를 미리 보여 주면 점수가 부푼다). 규격 같은 속성뿐 아니라 "본품인가 부속품인가", "새 제품인가", "모델 코드가 끝까지 같은가"처럼 물건의 정체를 묻는 줄도 넣는다.
- **제목·결론**은 1부 형식의 사실 서술만 쓴다. 예: "같은 모델의 시중가 대비 1.5배", "동급 벤치플룸관 시중가 대비 1.6배". 배율은 소수 첫째 자리까지 남기고 내림한다(부풀리지 않는다).

## 5. 에이전트의 도구

글은 LLM이 쓰고, 근거를 조회하거나 첨부할 때는 코드로 된 도구를 쓴다.

| 도구 | 하는 일 |
|---|---|
| 원문 줄 조회 | 판매 페이지의 줄 번호 원문을 돌려준다(탐지된 지시문은 빠져 있다) |
| 조달 물품 정보 조회 | 조달 물품의 이름·규격·단위·단가를 돌려준다 |
| 사이트 정책 조회 | 사이트 정보 저장소(8절)에서 그 사이트의 부가세 정책을 돌려준다. 없으면 정책 페이지를 읽는다 |
| 근거 첨부 | 출처·줄 번호·글자를 받아 **그 줄에 그 글자가 있는지 그 자리에서 확인**하고 근거 ID를 돌려준다. 없으면 거절하므로 LLM이 실행 중에 고칠 수 있다 |
| 계산기 | 식을 분수로 정확히 계산한다(+ − × ÷, 괄호, `ceil`, `floor`). 숫자·연산자만 받는 파서이고 범용 실행은 없다. Go `collector/cmd/studiocalc`(11/05) |
| `submit_answer`(실행기) | 에이전트 답(`agent-answer.schema.json`)을 받는다. 형식이 틀리면 오류 목록을 돌려준다. 받으면 코드가 만든 제목·결론을 돌려준다 |
| `review_title`(실행기) | 코드가 만든 제목·결론에 대한 동의 여부와 보충을 받는다(제목 더블체크) |

조달 물품 정보 조회는 **납품 단가 P를 주지 않는다**(11/05). 비교 단가 계산에는 P가 필요 없고, 라벨을 정하기 전에 배율에 끌리지 않게 하려는 것이다. 가격 차이 판정 도구도 주지 않는다. 사이트 정책 조회는 지금 정책 페이지가 없어 늘 "확인된 정책 없음"을 돌려준다(12절).

제출 도구와 토큰은 주지 않는다. 근거 첨부 도구는 "그 글자가 원문에 있다"만 보장하고 "그 근거가 주장과 맞다"는 보장하지 않는다. 그건 6절의 값 비교가 맡는다.

도구는 Python으로 된 MCP 서버 하나가 제공한다(13절). 근거 첨부 도구는 발급한 근거 ID를 실행 디렉터리의 발급 기록 파일에 남기고, 실행 뒤 확인과 채점이 그 파일을 읽는다.

## 6. 코드의 확인

### 객관 신호 (줄마다)

통과하면 그 줄은 접힌다. 하나라도 통과하지 못하면 에이전트를 여러 번 실행하고, **반복 결과가 일치해도 그 줄은 펼친다.** 일치도는 숫자로 보여 줘 사람의 공수를 줄인다.

- 근거 ID가 근거 첨부 도구가 발급한 것인지
- 조달 값·판매 값과 비교 결과가 맞는지(예: 값이 다른데 "같음"이면 실패). 표기 맞추기는 `norm-v1`(`60mm` = `60T` 등). 물건의 정체를 묻는 줄(구성·상태)은 글자를 맞대 볼 값이 아니라 판단이므로 글자 비교를 하지 않고 판매 페이지 근거만 요구한다(11/05, 첫 실제 실행에서 찾은 빈틈). 상태는 리퍼비시·중고·전시품·반품 같은 표시가 없으면 새 제품으로 보고 `not_on_page`로 둔다(11/05 사용자 결정). 읽은 값 "환산"은 같은 단위라 1인 경우 조달 물품의 단위를 근거로 붙여도 된다
- LLM 계산식을 코드가 다시 계산한 값과, 코드가 읽은 값으로 계산한 비교 단가가 같은지. 식은 같고 산수만 틀렸으면 산수 실수로, 식이 다르면 이해 차이로 기록한다
- 근거로 쓴 줄이 숨은 줄인지(`주의` 경고)

### 사건 단위 확인

- **필수 속성 누락.** 목록의 속성에 줄이 없으면 실패다. 객관 신호는 있는 줄만 확인하므로, 이게 없으면 중요한 줄을 빼먹은 답안이 자동 통과할 수 있다.
- **부가세 두 가정.** 페이지에 부가세 표기가 없으면 기본은 포함으로 가정한다. 코드가 포함·별도 두 가정으로 다 계산해 결론(가격 차이 기준 통과 여부)이 바뀌면, 에이전트가 사이트 정책을 확인한다. 확인하지 못하면 사람에게 넘긴다.
- **제목 더블체크.** LLM이 코드 틀의 제목·결론에 동의하지 않으면 사람에게 넘긴다.
- **단정 표현 검사.** LLM이 쓴 모든 글(판정 이유, 보충, 보류 사유)에서 "부당", "과다 지급" 같은 단정 표현을 찾는다(CLAUDE.md 규칙 6). 표현 목록은 구현할 때 정한다.

### 경고 단계

| 단계 | 조건 | 처리 |
|---|---|---|
| `danger` | AI에게 하는 말이 있다. 숨김 여부와 의도(선의·악의)를 가리지 않는다 | 사건을 자동 통과와 점진적 자동화에서 **늘 뺀다**. 그 글은 에이전트 입력에서 뺀다 |
| `주의` | 근거로 쓴 줄이 화면에 안 보이는 줄이다 | 그 줄을 펼친다 |
| 표시만 | 숨은 글이 있다 | 화면에 표시만 한다 |

실제 사이트는 탭·메뉴에 `display:none`을 흔히 쓰므로 숨은 글 자체는 `danger`로 보지 않는다. AI에게 하는 말은 "AI"라는 낱말이 아니라 "AI를 부르며 무언가를 시키는 꼴"로 잡는다("AI 화질 개선" 같은 상품 설명은 걸리지 않게). 코드 규칙은 표현을 바꾸면 우회되므로, 놓친 지시문은 객관 신호가 다시 막는다.

가격 문의만 있는 페이지는 경고 없이 근거 부족으로 넘긴다.

## 7. 처리 규칙 (자동 통과 / 사람)

위에서부터 확인해 처음 걸리는 곳에서 사람에게 보낸다. 이유는 모두 기록한다.

1. `danger` 경고가 있다 → 사람(점진적 자동화에서도 영구 제외)
2. 필수 속성 목록이 없는 새 품목이다 → 사람
3. 라벨이 판단 보류다 → 사람
4. 펼쳐진 줄이 하나라도 있다 → 사람(반복 일치도와 함께)
5. 부가세 가정에 따라 결론이 바뀌는데 정책을 확인하지 못했다 → 사람
6. LLM이 제목·결론에 동의하지 않았다 → 사람
7. 결론이 "시중가 대비 N배"다 → 사람(지금은 항상)
8. 필수 속성 목록의 속성에 대조표 줄이 없다 → 사람
9. LLM이 쓴 글에 단정 표현이 있다 → 사람
10. 나머지(모든 줄이 접히고 결론이 "지적할 것 없음") → **자동 통과**

11. 페이지에 가격 꼴 글(`N원`, `₩N`, 배송 안내 줄 제외)이 있는데 근거 부족이라 하거나, 같은 물건이라면서 가격을 읽지 않았다 → 사람(11/05)

이유를 모두 기록하므로 순서는 처리 결과를 바꾸지 않는다. 8번과 9번(6절의 사건 단위 확인)은 4번·7번을 가리키는 참조가 바뀌지 않게 뒤에 붙였다. 11번은 이미 쓴 답안지의 번호(10번 = 자동 통과)가 바뀌지 않게 10번 뒤에 붙였다. 11번은 v2 합성 데이터에서 규칙 기준선이 "근거 부족"으로 놓친 19건이 모든 줄이 접힌 채 자동 통과한 데서 나왔다: 객관 신호는 "있는 근거가 맞는가"만 보므로 "근거를 못 찾았다"는 답은 막지 못한다.

**점진적 자동화.** 4번과 7번은 에이전트가 성숙하면 조건을 완화한다. 7번(가격 차이 있음 방향)은 "지적할 것 없음" 쪽보다 엄격한 기준을 둔다. 1번은 완화하지 않는다. 사람이 펼쳐진 줄을 판정할 때마다 "일치도 숫자 ↔ 사람 판정"이 짝으로 쌓이고, 이게 기준을 정하는 데이터가 된다. 완화 기준의 형식(무엇을 기록하고 어떤 꼴로 판단하나)은 [`scoring.md`](scoring.md) 6절에 있고, 숫자는 실데이터와 사람 판정이 쌓인 뒤 정한다. 합성 페이지는 표기가 고르므로 4번과 7번 모두 완화의 근거는 실데이터에서만 얻는다.

## 8. 사이트 정보 저장소

- 확인한 사이트 정책(부가세 표기 방식 등)을 가벼운 저장소에 남겨 같은 확인을 반복하지 않는다.
- 한 항목이 그 사이트의 모든 사건에 영향을 주므로, **저장하기 전에 사이트당 한 번 사람이 확인한다.**
- 값과 함께 근거(인용, 원문 해시, 확인일)를 저장한다(CLAUDE.md 규칙 1).
- 유효기간과 저장 기술(SQLite, JSON 파일 등)은 워커 저장소와 함께 정한다.

## 9. 실행 기록

모델 이름, 프롬프트 버전, 입력 원문 해시, 줄 나누기 규칙 버전, 실행 횟수, 도구 호출 횟수, 입력·출력 토큰, 비용, 걸린 시간, 실행 시각. 실행기가 붙인다. 프롬프트 버전별 점수 비교와 건당 비용에 쓴다.

## 10. 채점과의 관계

- **① 근거 검증**: 위 6절의 확인을 그대로 쓴다. 정답 없이 돌아가므로 실데이터에도 쓸 수 있다. 에이전트 실행 중에는 안전장치, 평가 때는 점수다.
- **② 정답 대조**: 라벨과 코드 계산(비교 단가, 가격 차이 기준)을 `cases.jsonl`과 비교한다. 정답 파일의 "해야 할 일"은 대회 선점 상태를 반영하므로(건너뜀 6건), 채점기는 라벨과 `gap_pass`로 기대 결론을 다시 만든다. 정답의 차이 속성(생성기에 더할 칸)과 대조표를 맞춰 "맞는 이유로 맞혔나"(이유 점수)도 본다.
- 채점기는 에이전트와 같은 판단 로직을 쓰지 않는다. 답안지, 근거 발급 기록, 정답 파일을 **읽기만** 하고 ① 확인을 다시 돌리지 않는다. ① 근거 검증 점수는 실행 때 답안지에 기록된 결과를 쓴다. 실행기가 확인을 빠뜨리거나 잘못 기록하는 경우는 채점이 아니라 확인 코드와 실행기의 테스트가 잡는다.
- 지표, 점수표, 반드시 0건 조건, 완화 기준의 형식은 [`scoring.md`](scoring.md)에 있다.

## 13. 구현 구성 (언어, 도구 서버, 스키마, 저장, 위치)

- **언어.** 백엔드(입력 준비, 도구, 확인 코드, 실행기, 채점기)는 Python이고 웹 화면은 TypeScript다. 기존 Go 코드(1부 `collector`, 가짜 서버)는 다시 짜지 않고, 작은 함수 단위로 Python 쪽에서 부른다.
- **도구 서버.** 에이전트의 도구(5절)는 Python으로 된 MCP 서버 하나가 제공한다. 전체 인터페이스는 Python이고, 일부 도구가 안에서 Go 코드를 부른다.
  - 판단 로직은 Python 라이브러리(`studio/sheet`)에 두고, MCP 서버는 도구만 노출하는 얇은 껍데기다. 실행 뒤 확인(6절)과 처리 결정(7절)은 실행기가 라이브러리를 직접 부른다.
  - 연결은 stdio다. 에이전트가 MCP 서버를 자식 프로세스로 띄우므로 네트워크 포트가 없다.
  - 도구 서버는 에이전트 쪽이라 정답 파일(`cases.jsonl`)을 읽지 않는다(CLAUDE.md 규칙 4). 읽을 수 있는 경로를 제한하고 테스트로 확인한다.
  - 도구가 돌려주는 판매 페이지 글은 데이터다. 탐지된 지시문을 뺀 뒤 돌려준다(3절).
  - Go는 `collector/cmd/studiocalc` 실행 파일 하나다(11/05). 표준 입력 JSON 하나 → 표준 출력 JSON 하나이고 네트워크·토큰·파일을 쓰지 않는다. `eval`(계산기, MCP로 노출), `benchmark`(읽은 값 → 비교 단가), `gap`(1부 `claim.Evaluate`로 가격 차이 기준·예상액)이 있고 뒤의 둘은 실행 뒤 코드 계산에서만 쓴다. 1부 `claim`이 `collector/internal`에 있어 이 위치여야 한다.
  - 도구 서버는 사건마다 프로세스 하나다. 띄울 때 받은 사건의 페이지와 조달 물품만 보여 준다. 실행기는 도구 서버에 API 키를 넘기지 않는다.
- **스키마.** 원본은 JSON Schema 파일(`studio/schema/`: 답안지, 에이전트 답, 사람 판정)이다. 언어마다 로더·파서를 API로 두고(지금은 Python `studio_schema`: 불러오기·검증·금액 파싱), 공용 예시(`examples/<스키마>/valid·invalid`)를 모두 같은 결과로 받아들이고 거절하는지 시험한다. 웹 화면은 같은 파일에서 타입을 만든다(`npm run gen:types`). MCP 도구의 입력 형식도 JSON Schema로 선언한다. 금액과 비용은 십진 문자열 패턴으로 받아 float가 들어올 수 없게 한다. 칸 사이의 규칙(근거 ID가 근거 목록에 있는가 등)은 확인 코드가 맡는다.
- **저장.** JSON 파일로 둔다. 실행마다 디렉터리 하나, 사건마다 답안지 하나다. `studio/demo/`는 gitignore 대상이다. 파일 이름은 구현할 때 정한다.

  ```
  studio/demo/runs/<실행 ID>/
    run.json                          실행 정보(모델, 프롬프트 버전, 사건 목록, 비용)
    <case_id>.json                    답안지(사건마다)
    logs/<case_id>.evidence.<n>.jsonl 근거 발급 기록(n번째 실행, 근거 첨부 도구가 쓴다)
    logs/<case_id>.calc.<n>.jsonl     계산기 호출 기록
    judgments/<case_id>.json          사람 판정(검토 화면이 쓴다)
    scorecard.json, scorecard.md      점수표(채점기가 쓴다)
    relaxation-records.jsonl          완화 기준 기록(채점기가 쓴다, scoring.md 6절)
  ```

  사이트 정보 저장소(8절)와 사람 판정 기록의 저장 기술은 워커 저장소와 함께 정한다.
- **위치와 의존 방향.**

  | 위치 | 내용 |
  |---|---|
  | `studio/schema/` | 답안지 JSON Schema |
  | `studio/sheet/` | Python 라이브러리(입력 준비, 확인 코드, 코드 계산)와 MCP 서버 진입점 |
  | `studio/grader/` | 채점기([`scoring.md`](scoring.md)) |
  | `studio/agent/` | 에이전트 실행기(공급자 무관 도구 루프, OpenAI Responses API 어댑터가 기본·Anthropic 어댑터 선택)와 규칙 기준선 |
  | `studio/review/` | 웹 검토 화면의 백엔드(Python 표준 라이브러리 HTTP, 루프백만) |
  | `studio/web/` | 웹 검토 화면(Vite + React + TypeScript) |

  `studio/sheet`와 `studio/grader`는 생성기(`studio_synth`)를 가져다 쓰지 않고, `studio/grader`는 `studio/sheet`도 가져다 쓰지 않는다(11/05). 생성기의 계산 함수를 빌려 쓰면 같은 함수끼리 비교하게 되어 채점 명세 3.4절의 "계산 규칙 차이"가 늘 0건이 된다. 테스트로 확인한다. 채점기는 정답을 `cases.jsonl` 파일로만 읽는다.
