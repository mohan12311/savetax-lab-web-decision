## 지금 이어서 할 일 (2026-11-03 기준)

사용자가 먼저 생각을 말하고, Claude는 그 뒤에 의견을 붙인다(CLAUDE.md 「작업 방식」).

### 11/03에 정한 것 (이유와 버린 안은 아래 결정 이력)

- **다음 작업 순서**: A(평가)와 B(에이전트)를 한 묶음으로 하고, 순서는 답안지 양식 → 채점기 → 에이전트. D(웹 화면)는 그 뒤, C(1부 게이트의 hard-05 파렛트 환산 문제)는 뒤로 미룬다.
- **채점**: ① 근거 검증(답안을 보관 원문·조달 물품 정보와 대조, 정답 불필요)과 ② 정답 대조(`cases.jsonl`, 합성 데이터에만 있음)를 둘 다 둔다. 채점기는 에이전트와 같은 판단 로직을 쓰지 않는다.
- **2부의 상정**: 대회 제출이 아니라 실제 사용자의 검증 도구로 쓸 수 있는가. 선점된 건도 대상이다.
- **답안지 양식**: 8개 항목을 모두 정했다. 명세는 [`studio/docs/answer-sheet.md`](../studio/docs/answer-sheet.md)에 있다. 요지: 라벨 5종(판단 보류 포함)만 LLM이 내고 가격 차이는 코드가 계산한다. 속성 대조표의 줄마다 코드가 확인해 접거나 펼친다. 근거는 줄 번호 + 글자로 도구가 확인해 ID를 준다. 위험(`danger`)·판단 보류·펼친 줄·"시중가 대비 N배" 결론은 사람에게 가고, 나머지는 자동 통과한다.
- **결정 2(ADR)**: 결정마다 ADR을 두지 않는다. 설계의 현재 모습은 명세 문서에, 어떻게 정했는지는 이 문서의 결정 이력에 적는다.

### 다음에 정할 것 (함께 정할 결정)

채점기를 만들기 전에 정한다.

- **평가 지표**: 판정 정밀도·재현율, 비교 단가 정확도, 가격 차이 오판율, 건당 비용·지연. 판단 보류를 어떻게 셀지(보류율과 보류하지 않은 건의 정확도를 함께 볼지), 자동 통과한 사건 가운데 틀린 비율, 다른 물건을 "맞는 이유로" 맞혔는지(정답의 함정 칸과 대조표). 점진적 자동화의 완화 기준도 여기서 나온다. 합성 점수와 실데이터 점수는 따로 표시한다.
- **구현 언어와 위치**: 답안지 스키마·확인 코드·채점기를 어느 언어로 둘지. studio는 생성기가 Python, 가짜 서버가 Go이고, 1부 금액 계산(`claim.Evaluate`)은 Go다.

그다음은 정해진 범위 안의 구현이다: 답안지 JSON 스키마, ① 확인 코드, 채점기.

### 그 뒤에 정할 것 (아직 다루지 않음, 순서도 미정)

- 에이전트 범위: 판매처 페이지를 **찾는 일**까지 할지, 주어진 후보 페이지를 **판정**만 할지. 찾기까지 하면 가짜 판매처에 검색이 필요하다.
- 도구와 권한의 세부: 도구 후보는 명세 5절(원문 줄 조회, 조달 물품 정보 조회, 사이트 정책 조회, 근거 첨부. 제출 도구는 없음). 정책 페이지를 읽을 때 같은 사이트 안으로만 제한할지 등. 가짜 판매처에 정책 페이지가 있어야 하고, 그 페이지도 주입 경로가 될 수 있다.
- 모델과 비용: 이야기한 기본안은 Haiku 5.5로 1차 판정, 애매한 건만 Sonnet 5.5로 올리기. 반복 실행의 횟수와 모델, 한 번 실행할 때의 비용 상한, 캐시. `ANTHROPIC_API_KEY`는 환경변수나 키체인에서만 읽는다.
- 가상 렌더링 머신(11/03 사용자 요청, **미래의 개선 사항**으로 미룸): 헤드리스 브라우저로 JS 페이지를 그려 LLM에게 준다. 따질 점: 지금 정답 파일은 "JS 페이지는 못 읽는다"를 전제로 빈 페이지 5건을 근거 부족으로 둔다(가짜 판매처는 `/static/app.js`를 내주지 않는다). 렌더러를 넣으면 가짜 판매처가 실제로 그려지는 스크립트를 내주고 생성기의 정답도 바뀌어야 한다. 그린 결과(DOM)를 원문으로 보관·해시한다. 남의 자바스크립트를 실행하므로 데모에서는 외부 요청을 막는다(CLAUDE.md 규칙 3). 봇 차단을 우회하는 수단으로 쓰지 않는다. 지금까지 studio는 표준 라이브러리만 썼는데 큰 의존성이 생긴다.
- 합성 데이터 보강: 가격은 있는데 부가세 표기가 없는 사례(지금 표기 없는 8건은 모두 가격 자체가 없다), 가짜 판매처의 사이트 정책 페이지(명세 12절).
- 워크플로우의 끝: 1부의 가짜 제출을 계속 끝 단계로 둘지, 검증 결과(보고서)가 끝인지. 11/03 "실제 사용자의 검증 도구"로 상정을 바꾸면서 생긴 질문이다. 실제 사용자를 누구로 상정할지도 함께.
- 사람의 결정이 실제로 작동하게 하는 화면 정책: "다른 물건" 판정에도 가격 차이를 보여 줄지(배율이 사람을 끌어당길 수 있지만, 잘못된 "다른 물건"을 잡을 단서도 된다). AI 답을 먼저 보여 주면 그대로 승인하기 쉬운 문제(자동화 편향)를 어떻게 줄일지.
- 웹 화면의 사용자 구상(11/03): 대조표의 줄이 신뢰도에 따라 자동으로 접히거나 펼쳐지고, 줄을 열면 인용·출처 같은 근거가 보인다. 확신이 높아도 라벨을 결정한 줄은 펼쳐 둘지는 화면 단계에서 정한다.
- 1부 게이트 한계(hard-05) 처리: 게이트를 고칠지(단위 환산을 근거에 명시하면 통과), 사람에게 넘길지.
- 작업 대기열·상태 전이·재시도·비용 상한(워커), 사이트 정보 저장소의 유효기간과 저장 기술, 웹 화면 스택(TypeScript 쪽으로 이야기했다).

### 사용자에게 남은 일
- 대회 확정 결과 확인: `make check`가 `SAVETAX_TOKEN` 값 문제(4글자짜리 값이 남아 있음, `.env` 또는 키체인)로 실패했다. 값을 정리한 뒤 사용자가 직접 확인한다. 결과가 나오면 README 「결과」 절을 고친다.
- 운영진 회신을 기다린다(대회 데이터셋의 대회 후 이용 범위). 회신에 따라 실데이터 평가 여부를 정한다.
- 비공개 저장소의 공개 전환 여부
